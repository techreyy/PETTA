# Performance audit - 2026-10-03

Status: implemented locally; NOT pushed. Functional checks pass, but the no-performance-regression release gate is not established. Local timings vary substantially between unchanged baseline runs, some final timings are worse, and the production Neon connection has not been tested with the new configuration.

## Changes retained

- `getDatabaseConfig()` normalizes standard Neon `ep-...neon.tech` endpoints to the corresponding `-pooler` endpoint, preserving credentials, database, query parameters and strict TLS. Already pooled endpoints remain unchanged; other providers and local hosts remain unchanged.
- Payload 3.90.2 `getPayload({ config })` already caches the instance and in-flight initialization promise. Its Postgres adapter creates its pool only when absent. No runtime pools were added. The existing inquiry limiter retains its separate bounded, reused pool.
- Project detail uses depth 1 instead of 2: media, gallery, category and SEO fields needed by rendering remain populated. Project and news detail skip unused pagination counts while retaining `limit: 1` and published-only access checks.
- Project detail starts the shared content read and detail read concurrently. Existing React request memoization remains; no persistent content/session/user cache was introduced.
- `PETTA_CMS_TIMING=true` enables Local API operation durations outside production. Production always returns the original Payload object, even if this flag is accidentally enabled. Labels contain operation/collection and duration only, never query arguments, records, credentials or session data. Services are also instrumented.
- A candidate shared request/DataLoader optimization was removed after its listing measurements worsened. It is not part of the final code.

No design, features, schema, content, auth rules, R2 configuration or upload implementation changed. No migrations or required new environment variables. Prefer an explicitly pooled `DATABASE_URI` in deployment configuration; runtime normalization also handles standard direct Neon hosts. Actual deployed hostname/connection health still require verification.

## Measurement method

Windows, Node 22.23.3, Next production Webpack builds, local PostgreSQL with the existing studio catalog. Baseline source is commit `e7dd507`; the repeat rebuilt the original affected files from HEAD and restored the optimized files afterwards. Each local route has a first request plus 15 subsequent sequential requests, reporting median and nearest-rank p95. Only the first homepage request is application-cold; later first requests are route-cold in a warm process. Measurements exclude browser rendering, hydration and image downloads.

Queries measure complete Payload Local API operations, including relationship population; they are not isolated SQL execution times. `media` and category aggregates include nested relationship reads. Admin uses the same production build with an independently seeded disposable local database and temporary QA owner. Login/session tokens never enter reports; the QA database is removed afterwards. No studio accounts are changed.

All catalog/detail/SEO outputs have the identical SHA-256 across baseline, repeat and final: `69087b404b76174bf4e89dbf34ad1751444a9f571ad5d2db020aa87590ae7c91`. Public response byte lengths also match. This verifies data equivalence, not visual browser QA.

## Verification and reproduction

TypeScript, ESLint, production build and 70 automated checks pass: 30 database/unit, 18 content/editorial, 3 services loader, 10 rendering/accessibility/status, 2 gallery, 3 services page and 4 startup. Rendering tests emit the existing mock Motion `layout` attribute warning. Authenticated HTTP dashboard and `/api/users/me` succeed; an anonymous request returns `user: null` after authenticated requests. No user/session cache was introduced. Live responsive browser QA was unavailable.

Local build generates types without `_objectKey` when S3 environment variables are absent. That build side effect was restored to the committed production type definition; no media/type/schema change is part of this patch.

Run a production build, then:

```powershell
node --env-file-if-exists=.env.local --import tsx scripts/performance-audit.mjs audit-label
node --env-file-if-exists=.env.local --import tsx scripts/performance-admin-audit.mjs audit-label
```

Both scripts reject non-local database hosts. The first reads the existing catalog; the second creates/drops only its own `petta_test_<timestamp>` database. Raw reports and server logs are in ignored `.cache/performance/`. Development timing: set `PETTA_CMS_TIMING=true` and run the existing development command; unset it after the audit. Production timing remains disabled unconditionally.

Release remains held until representative measurement resolves the observed regressions and the intended Neon pooled endpoint is verified against the deployed environment. No commit or push was performed.
