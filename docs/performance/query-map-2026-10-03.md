# Root layout and page query audit

Audit date: 2026-10-03. Scope: the current working tree, including the previous unpushed performance patch. This is a source-level query/dependency audit, not a new production timing run. No runtime code is changed by this audit.

## Findings, in priority order

### High: every public page waits for the complete studio catalog

`src/app/(site)/layout.tsx:47` awaits `getContent()` before returning the layout. `src/lib/content.ts:145` starts eight main Local API operations in parallel: projects, categories, news, settings, team, awards, competitions and brand logos. The layout therefore waits for the slowest operation even if its data is unrelated to the current page. With force-dynamic at layout line 40, this cost applies to fresh server renders. Client navigation can reuse layouts; these counts must not be multiplied blindly by every click.

Header needs category title/slug and studio settings (`src/components/Header.tsx:45`). Footer needs studio settings (`src/components/Footer.tsx:11`). Neither requires the entire project/news/team/awards/competition catalogs or partner logo rows. Contact and the legacy export page demonstrate the unnecessary work most clearly.

The eight calls use Promise.all already: they are not eight sequential round trips. Relationship population can add database operations, so eight Local API calls is not an exact SQL-query count.

### High: root providers serialize unrelated data to every public page

`src/app/(site)/layout.tsx:63` passes settings, projects, categories, news, team, awards and competitions into Client Component providers. `src/lib/ProjectContext.tsx:29` stores all six catalogs together. Brand logos are embedded in `settings.editorial.logos` (`src/lib/content.ts:246`), although only HomeView consumes them.

This adds server transformation and RSC serialization work plus transfer/client parsing costs beyond database latency. Moving a page's fetch alone will not fix this while the root provider still loads all catalogs.

### Medium: sitemap performs eight rich reads for three slug lists

`src/app/sitemap.ts:6` uses getContent but only maps project/category/news slugs. It does not need settings, team, awards, competitions, logos, populated media or card metadata. It is outside the public layout, so this is its own unnecessary batch, not a duplicate layout invocation.

### Medium: listing queries fetch more rows/fields than several consumers need

All shared lists use pagination:false and no explicit limit. Projects already exclude gallery/description/SEO; news excludes body/SEO. These are useful existing protections, but the loaders still return the complete published catalogs and other unselected fields, plus relationship documents.

HomeView only displays five hero projects, three built projects, six featured projects and three news items. Its category totals depend on the full project set, however. Portfolio filters and related-project selection also depend on current full-list ordering/content. Do not add a global limit to getContent: it would change features, counts and related results. Separate projections and page-specific selection are required before limiting reads safely.

Category pages filter the full project list in memory (`src/app/(site)/portfolio/category/[slug]/page.tsx:25`). The predicate includes a legacy category-title-derived slug fallback; a future database filter must preserve that behavior. Repeated category counting in getContent is O(categories * projects), a lower-priority CPU concern than the broad data reads.

### Medium: admin permission evaluation can repeat a users count

`src/cms/collections.ts:26` calls payload.count(users) in Users.access.create for every non-owner, including an anonymous login-page request. Installed Payload 3.90.2 evaluates create permissions in getAccessResults. Its root layout and root page call initReq with different full-request keys (`RootLayout` and `initPage`), and each evaluates permissions. This exposes repeated count work during one render for anonymous/non-owner contexts; exact runtime counts still require instrumentation.

The login/root-page flow separately performs db.findOne(users) to detect initial setup when req.user is absent. An authenticated owner bypasses the custom count; owner-only dashboard timings from the earlier audit do not establish admin/editor performance. The first-register API guard also counts users, but only on that specific endpoint, not on every admin request.

These checks participate in bootstrap/auth behavior. Preserve them during this performance scope; do not cache account existence, users, sessions or access results across requests, patch node_modules, or weaken first-user registration protection. A future equivalent existence-query optimization would require explicit auth-behavior regression coverage.

## What is already correct

- getContent, getProject and getNews use React cache. Repeated page/layout/metadata invocations in the same server render are not evidence of duplicate database reads. This is request memoization, not a cross-request stale-content cache.
- The eight shared reads run concurrently. The previous local patch also starts project-detail and related-catalog reads together, uses detail depth 1, and avoids detail pagination totals. These changes remain unpushed and are documented in the earlier timing audit.
- getServices has no cache wrapper but currently only one page call site, so there is no demonstrated duplicate to optimize there.
- Payload getPayload reuses its initialized instance and pool. There is no helper-level new Pool in the public page path.
- Admin has a separate root, never calls getContent, and does not load the eight public catalogs through the application layout.

## Recommended implementation order

1. Split navigation/settings reads from page data. Keep only shared identity/contact and category navigation in the root; decouple homepage partner logos from global settings loading.
2. Place page-specific data/providers at page or appropriate route boundaries. Preserve provider values when navigating between pages; replacing unrelated root arrays with empty arrays alone would break client consumers.
3. Add narrowly selected sitemap slug reads at depth 0. Preserve published/active filtering and route coverage.
4. Narrow public card/media projections and homepage selections with tests for status filters, category counts, fallback behavior, ordering and related projects. Do not introduce pagination or alter visible selection rules.
5. Profile admin login and owner/admin/editor separately, including the non-owner users count. Leave native auth/session/access/lock freshness intact.

The public shell has a theoretical two-operation floor (settings + category navigation); page data adds only relevant reads. This is a design target, not an implemented/measured new query count. Shared category needs and count computation must be reconciled to avoid replacing overfetching with duplicate reads.
